




### FreeRTOS的中断处理流程

FreeRTOS 处理中断的核心思路就一句话：中断服务程序里只干最少的活，把真正耗时的事情甩给任务去做。具体来说，中断进来之后，ISR 里只做三件事——清标志、读数据、通过 FromISR 系列的专用 API 把数据或者信号丢进队列或信号量里，然后调一个 portYIELD_FROM_ISR 就完事了。这个 portYIELD_FROM_ISR 并不是当场做上下文切换，它本质上只是把 PendSV 异常挂起，等所有中断全部退干净之后，PendSV 才真正触发，这时候才去保存旧任务的上下文、恢复新任务的上下文、完成切换。之所以要绕这一层 PendSV，是因为中断可能嵌套，如果在外层中断还没跑完的时候就切任务，栈就乱了。另外还有一个特别容易踩的坑，就是中断优先级配置，FreeRTOS 用 BASEPRI 寄存器做屏蔽，只有优先级数值大于等于 configMAX_SYSCALL_INTERRUPT_PRIORITY 的中断才允许调 FromISR API，高于这个阈值的中断如果调了，就会和内核操作同一条任务链表产生竞争，直接 HardFault。所以总结下来就是：硬件管中断进出，PendSV 管任务切换，FromISR API 管操作安全，优先级配置管系统生死，这四层搞清楚，中断这块基本就通了。


### PendSV是什么
PendSV 就是 Cortex-M 芯片里专门预留的一个"最低优先级的软异常"，你可以把它理解成系统给自己留的一个"收尾闹钟"。它的特点是优先级被故意设到最低，低到所有硬件中断都能打断它，但没有任何中断能阻止它最终执行。FreeRTOS 就是利用了这个特性——中断 ISR 里不直接切任务，只是把 PendSV 标记为"待处理"，然后 ISR 该干嘛干嘛，等所有中断全部跑完、CPU 闲下来了，PendSV 才自动触发，这时候再安安心心地做上下文切换。这样做的好处就是，不管中断嵌套了多少层，切换动作永远发生在"最外层中断退出之后"，栈绝对不会乱。说白了，PendSV 就是 FreeRTOS 跟 CPU 之间的一个约定：你帮我保证，等所有急事都处理完了，再叫我一声，我再慢慢换人干活。

### `.a`后缀的库

用过。 `.a`  就是静态库，本质上就是一堆 `.o` 目标文件打包在一起的归档文件，用 `ar` 命令生成的。我在项目里用过两种场景：一种是芯片厂商提供的 HAL 库或者 BSP 库，他们不想给你源码，就编译成 `.a` 丢给你，你在链接阶段把它链进去就行；另一种是自己团队内部封装的通用模块，比如通信协议栈、加密算法这些，为了复用和保密，也会编成 `.a` 给其他项目组用。用的时候就是在 Makefile 或者 CMake 里加一个 `-L` 指定路径、`-l` 指定库名，链接器就会从里面挑你用到的 `.o` 塞进最终的固件里。跟 `.so` 动态库的区别就是，`.a` 是编译时就把代码拷进你的可执行文件里了，运行时不再依赖外部文件，所以嵌入式里基本都是用静态库，因为 MCU 上根本没有操作系统去帮你做动态加载那一套。


### 指针和引用的区别

**指针**是一个独立的变量，它里面存的是地址，你可以随时让它指向别的地方，也可以让它为空（nullptr），声明的时候可以不初始化，用的时候必须手动解引用 `*p` 才能拿到值。

**引用**是变量的别名，声明的时候就必须绑定一个对象，一旦绑定了就不能再改，也不存在"空引用"这种东西，用的时候不需要解引用，写起来跟直接用原变量一模一样。
